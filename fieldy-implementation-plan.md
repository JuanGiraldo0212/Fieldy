# Fieldy implementation plan

This document is the brief for Claude Code. Read it fully, then create one task per checkbox in the milestone order below and implement them. Ask before deviating from a decision in sections 1 and 2. Everything in section 3 onward is the plan itself.

Companion files, already written and treated as inputs:

- `Full prototype build complete/outing-schema.md`: the catalog schema v2 (venue, program, images). Also authoritative. The catalog is maintained by us, never edited by users.
- `outputs/*.json`: preprocessed catalog records, one file per venue, already conforming to `outing-schema.md` — 15 venues, each with a `.verification.md` beside it and a `batch-summary.md` for the run. - `Full prototype build complete/Field Trip Planner Bright.dc.html`: **the design, and the visual source of truth.** See section 2a. When the design and this plan disagree, the design wins for layout, spacing, copy, visual states and interaction; this plan wins for data shape and edge cases, and `data-model.md` wins for field names and enums. When the design shows something this plan does not mention, build it as designed. When this plan requires something the design does not show (an error state, a loading state), build it in the design's language and list it in `docs/design-gaps.md`.

## 1. Goal and scope

Ship an MVP that an ECE or daycare director in Greater Victoria can use from a link on their phone to find a feasible outing, send a request to the venue through Fieldy, see the venue's reply in a thread, and confirm the trip in one tap.

In scope: catalog browsing without login, rooms, trips with date options and tasks, a send-only email relay (Fieldy to venue, venue back to Fieldy) with reply notifications to the educator, suggestion banners from venue replies, My trips, Inbox, saved outings, data correction reports, magic link auth.

Out of scope for this build: venue accounts or portal, payments, parent consent, multi user centres with permissions, transport booking, attachments parsing, mobile native apps, i18n, **and reply-by-email for the educator** — they read and write in the app.

## 2. Stack decisions

Chosen for speed of a solo build and a boring deploy. Swap only with a reason.

- **Next.js 15, App Router, TypeScript, React Server Components** for pages, Server Actions for mutations, Route Handlers for webhooks.
- **Supabase** for Postgres, Auth and Storage. Schema is managed with **Drizzle ORM** and drizzle-kit migrations against the Supabase Postgres connection (use the direct connection for migrations, the pooler for the app). Schema lives in `src/db/schema.ts`. Row Level Security is enabled on every user table with policies keyed on `auth.uid()`; the app reads and writes through Drizzle with the service role on the server only, and RLS is the safety net, not the primary access control.
- **Auth**: Supabase Auth magic link (email OTP link), `@supabase/ssr` for cookie sessions in Next.js. The `account` table has a foreign key to `auth.users(id)`. No passwords, no OAuth in the MVP.
- **Email**: Resend for outbound and inbound. Sending domain `mail.<domain>` verified in Resend; inbound receiving enabled on the same domain with the webhook at `/api/email/inbound`. Magic links are sent by Supabase Auth through Resend SMTP so transactional and relay mail are both on Resend but on separate subdomains (`auth.<domain>` and `mail.<domain>`) to keep reputations apart.
  - **The free tier is enough to build and demo on.** Verified September 2026: inbound receiving is included on every plan including Free; adding the MX record makes the domain receive at **any** address, which is exactly the catch-all `trip-<token>@` needs; a receiving subdomain is Resend's own recommended pattern when the apex already has MX. Free gives 3,000 emails/month, **100/day**, 3 domains, 10 req/s, 30 day log retention. We need 2 domains (`mail.` and `auth.`).
  - **Received email counts against the same quota as sent.** A trip costs 3 emails minimum (request out, reply in, notification out) and about 6 with one follow-up round, so 3,000/month is roughly 500 trips — irrelevant. **The 100/day cap is the real ceiling**, about 16 exchanges a day, and magic links share the pool. Two consequences: the demo seed script must never send real mail, and a pilot with more than a handful of centres moves to Pro ($20/month, 50k) before launch, not after.
  - Unverified, and therefore M4 test items rather than assumptions: the inbound message and attachment size cap (outbound is documented at 40MB, inbound is documented nowhere), and whether a venue's reply-all with CCs is counted as several received emails.
  - The inbound webhook carries **metadata only** — no body, headers or attachments. Fetch them with the Received Emails API and the Attachments API inside the handler (already how 5.4 is written).
- **No LLM and no Anthropic SDK.** The suggestion classifier is rule based (section 5.5). It is implemented behind a `SuggestionProvider` interface so a model backed provider could be added later without touching the UI.
- **Background work**: none. Inbound handling is fast enough to run inside the webhook (store, classify, notify) and the outbound send happens in the server action. Use Next's `after()` for the notification step so the webhook responds immediately. If a step fails it is recorded on the message (`send_error`, `notify_error`) and retried by a Supabase cron job (`pg_cron`) calling `/api/jobs/retry` every 5 minutes.
- **Maps and distance**: Mapbox Geocoding for address to lat/lng at room and centre creation. Distance is haversine in SQL. Travel minutes use the design's fixed speeds, not a routing API: **walking 4.6 km/h, bus 15 km/h plus a 9 minute wait, parent drivers 32 km/h plus 4 minutes**. Walking is not offered beyond 2.5 km ("too far with this group"). The catalog and program maps are an OpenStreetMap + Leaflet iframe, ported from `venue-map-bright.html`: dark pin for the room's home base, brand pin per venue, dashed polyline when a single venue is shown, `fitBounds` with 46px padding and `maxZoom: 15`. Programs with `comes_to_you` have no pin.
- **UI**: Tailwind and shadcn/ui as the base, themed entirely from the tokens in `docs/design-map.md` §3, which were extracted from the design (there is no token file). No hardcoded colours, radii or type sizes anywhere in components; if a value is not a token, add the token first. Type is **Bricolage Grotesque** (display) and **Nunito Sans** (body), self-hosted, not Google-hosted. Mobile first: build at 390px, then check 620px — the design's own breakpoint, below which the trip header rail and the room stat rows stack — then 768px.
- **Storage** for raw email source and attachments: Supabase Storage, private bucket `mail`, signed URLs generated at render time. Object keys stored on `message.attachments[].url` and `message.raw_ref`.
- **Testing**: Vitest for units, Playwright for three end to end flows (section 9). No snapshot tests.
- **Deploy**: Vercel for the app, Supabase for everything stateful, Resend for mail. Single production environment plus preview deployments pointing at a separate Supabase project. `.env.example` documents every variable.

Format: `<x-dc>` markup with `sc-if` / `sc-for` control tags and `{{ binding }}` expressions, all styling inline as hardcoded hex, and one `<script type="text/x-dc">` block at the bottom holding the state, the mock catalog, feasibility, task generation and the suggestion banners. It runs — open it in a browser and click through it before building anything.

**Only the bright theme ships.** `Field Trip Planner.dc.html` and `venue-map.html` are an earlier warm-palette variant, superseded and out of scope. Do not build it, do not carry a second theme in the tokens.

How to use it:

1. **Tokens first.** `docs/design-map.md` §3 lists every colour, type step, radius, shadow and control height, extracted from the prototype's inline styles. In M0, write those into `src/app/globals.css` as CSS variables and into `tailwind.config.ts`, and override shadcn's theme variables with the same tokens so every primitive is on brand without per-component styling. The spacing values in the prototype are not a clean 4pt grid — normalise to 4pt and log any visible drift as a gap.
2. **Components before screens.** `docs/design-map.md` §5 is the component inventory: design element → target path under `src/components/` → the states the prototype actually renders. Build each one with a dev-only gallery at `/dev/components` covering every listed state, and compare side by side against the running prototype before moving on.
3. **Screens compose components.** Section 6 of this plan maps each route to the line range of its prototype section. A route file should be mostly layout and data; if a screen needs a visual element not in the inventory, that is a gap — add it to `docs/design-gaps.md` and build a minimal version in the same language.
4. **Copy comes from the design, verbatim.** `docs/design-map.md` §7 is the full string inventory, including the feasibility issue sentences, the ask questions, the suggestion banner text and every empty state. Do not paraphrase and do not invent microcopy.
5. **Icons** are Lucide, 24×24, stroke-width 2, round caps, rendered at 15–20px. `docs/design-map.md` §4 lists the exact icon names and the category / practical-fact / travel-mode maps. Use `lucide-react` with those names.
6. **States the design does not show** (loading skeletons, network errors, form validation beyond "Pick at least one date.", the "sending" moment after tapping Send) are built with the design's tokens and the plainest possible treatment, and logged as gaps. §9 of the design map is the starting list.
7. **Motion is one keyframe.** `riseIn`: opacity 0 → 1 with `translateY(6px)` → none. Everything else is instant. Keep it that way.
8. **Two settings are declared on the design document itself** and are real product settings, not prototype scaffolding: `rankFeasibleFirst` (boolean, default true — sorts green above amber for every sort except Distance) and `taskBufferDays` (int, default 3, range 0–14 — the buffer in the send-request task offset).
9. **The simulate-a-venue-reply row on the trip page is prototype-only.** Do not build it. Its replacement is `scripts/simulate-venue-reply.ts` (M4).

Do not port the markup. Use it as a reference for structure, states and copy, then rebuild with the project's components so tokens and data flow stay consistent.

## 4. Data layer

### 4.1 Tables

Create Drizzle tables for every entity in `data-model.md` and `outing-schema.md`, with these implementation notes:

- ULIDs as text primary keys, generated in the app.
- Enums as Postgres enums, names exactly as in the data model.
- `trip.room_ids` as `text[]` with a check that it is non empty. Do not normalize into a join table for the MVP; the array is read whole every time.
- `date_option`, `ask`, `task` stored as `jsonb` columns on `trip`, validated by Zod schemas in `src/lib/trips/`. They are always read and written with the trip. `task` is the only one edited independently, and it is small enough to rewrite the array.
- `message.suggestion` as `jsonb`, nullable.
- `message.attachments` as `jsonb`.
- `trip.relay_token` text unique, 10 characters, base32 lowercase, generated at trip creation.
- `centre.rate_class` is a generated column from `type`.
- Indexes: `trip(centre_id, status)`, `message(trip_id, sent_at)`, `message(read_at) where read_at is null`, `trip(relay_token)`, `program(venue_id)`, a GiST or plain btree on `venue(lat, lng)` is enough at this size.
- Soft delete on `room` only, via `archived_at`. Enforce "at least one non archived room per centre" in the server action, not the database.
- `account.id` equals `auth.users.id`. A trigger on `auth.users` insert creates the `account` row with the email.
- `trip.status` is `requested · replied · confirmed · done · cancelled` exactly as the data model defines it. The design's status rail shows a leading "Idea" step and labels `requested` as "Asked" — drop the Idea step (a trip only exists once a request is sent) and keep the design's labels: **Asked** (requested) → **They answered** (replied) → **Confirmed** → **Done**, with the sublines "Request sent to the venue" / "Waiting on your call" / "Date is locked in" / "You went". `cancelled` is not on the rail. Log the dropped step in `docs/design-gaps.md`.
- **Renaming an enum value needs a hand-edited migration.** drizzle-kit generates a drop-and-recreate that is wrong twice over: it casts an array column to `text` rather than `text[]`, which Postgres rejects outright, and it does nothing about rows holding the retired value, so the cast back to the new enum fails. Add an `array_replace` (or plain `UPDATE`) while the column is text, and replay `0000` onward against an empty database before committing. `0002` is the worked example.
- `room.icon` is the enum `baby · backpack · cap · users`, rendered as the tinted avatar; the tint pairs are in `docs/design-map.md` §3.1.
- RLS policies: `account` self only; `centre`, `room`, `trip`, `message`, `saved_outing` visible where the row's `centre_id` matches the caller's account centre; catalog tables readable by `anon` and `authenticated`, writable by nobody except the service role; `report` insertable by `anon`.

### 4.2 Derived values

Implement in `src/lib/trips/derived.ts` and never store:

- `total_cost = children_count * cost_child + adults_count * cost_adult + cost_group_fee + cost_transport` with nulls treated as 0 and a flag `cost_incomplete` when any component is null.
- `required_adults = sum over rooms of ceil(room.size / room.ratio_children_per_adult)` using room values snapshotted at creation (store `room_snapshots` jsonb on the trip: id, name, size, ratio).
- `waiting_on`: `venue` if the last message is from the educator, `educator` if the last is from the venue, `nobody` if status is confirmed, done or cancelled. Labels from the design: "Waiting on venue" / "Your turn".
- `days_waiting` from the last message timestamp.
- `overdue_tasks` count from tasks with `due_date < today and not done`.
- `bucket`, which drives the My trips tabs: `past` if status is done or cancelled; else `needs` if the last message is from the venue; else `waiting` if a request is out and unanswered; else `upcoming` if confirmed. Saved outings are a separate list, not a bucket.

### 4.3 Catalog import

The catalog JSONs in `outputs/` are already in the shape of `outing-schema.md` — 15 venues, each with a sibling `.verification.md` the import ignores. `scripts/import-catalog.ts`:

- Generates a Zod schema from `outing-schema.md` (write it by hand in `src/lib/catalog/schema.ts`, field for field) and validates every file. A file that fails validation aborts the whole import with the path and the error; partial catalogs are worse than none.
- Upserts venues by `slug` and programs by `(venue_slug, program.slug)` in one transaction. Fields present in the JSON overwrite the database; fields absent from the JSON are left untouched, so hand edits to columns the JSON does not carry survive re-imports.
- Programs present in the database but missing from the JSON for that venue are marked `active = false`, never deleted, because trips reference them.
- Image references in the JSON are copied as is; images themselves are served from wherever the schema says, the import does not upload anything.
- Emits a diff report to stdout: new venues, new programs, changed prices, deactivated programs, and validation warnings.
- Runs with `pnpm import:catalog` locally against any Supabase project via `DATABASE_URL`. It is also the only way catalog data enters the system; there is no admin UI in the MVP.
- Resolves one booking address per program at import time: `program.booking_email` when the schema carries it, otherwise `venue.booking_email`. Schema v2 has both, program level overriding venue level.

## 5. Core behaviours

### 5.1 Feasibility (`catalog/feasibility.ts`)

Input: a program with its venue, and a room (or the anonymous search state when logged out). Output: `{level: 'green'|'amber', reasons: string[]}`.

**Two levels, not three.** The design has no red state: a card is green when nothing failed and amber otherwise, with every failed reason joined by ` · ` on one line. Do not add red.

**Three checks only** — age, capacity, budget. Distance and season are *filters*, not feasibility reasons: a program outside the radius or out of season is excluded from the results, not badged.

**A missing fact is not a failure.** Only a known mismatch goes amber. "The venue did not publish its capacity" is not evidence that the group will not fit; it is evidence that nobody has asked yet.

This was measured against the real catalog, not assumed. Counting unknowns as failures returned **zero green programs out of thirty-nine**: 33 publish no capacity, 18 no youngest age, 13 no price, and only 9 of the 94 reasons raised were an actual mismatch. A badge that is always amber carries no signal and trains people to ignore it, which costs them the real failures it exists to surface. With unknowns excluded the badge discriminates properly — 17 of 39 green for a preschool room, 35 of 39 for a school-age one.

The unknowns are not swallowed. They still render as "Capacity not published" / "Price not published" / "Ages not published" on the card and the outing page, and they still become pre-selected asks on the request (5.2), which is where a director can act on them. Surfaced twice is enough; they do not also need to consume the badge.

The reason strings are copy and ship verbatim:

- age, first match wins:
  - `age_basis = 'grades'` and the room's `age_max <= 5` → `ages are set by grade here, not years — phone to confirm they take under-fives`. This is a **known** mismatch, not a missing fact: the venue published a range, in units that cannot answer the question this room is asking.
  - `age_min_years` is not null and `> room.age_min` → `built for {n}+, your youngest are {n}`
  - Never convert grades to years anywhere, for this check or any other. Flag the mismatch instead of guessing.
- capacity: `capacity_max` is not null and `< room.size` → `capacity is {n}, your group is {n} — ask about splitting`
- budget, on effective cost per child (`cost_per_child_cad`, or `cost_per_group_cad / size`): not null and over `budget_per_child` → `{$} a child is over your {$} budget`

Badges: green renders `Fits your group` on the card and `✓ Fits {room name}` on the outing page; amber renders `One thing to check` on the card and `! {reasons}` on the outing page.

Sorting: `rankFeasibleFirst` (default true) puts green above amber for **Best match**, **Duration** and **Price**, then applies the sort key, then distance as the tiebreak. **Distance: nearest** ignores the green ranking entirely and sorts purely by distance.

### 5.1a Catalog search and filters (`catalog/search.ts`)

The design's catalog is richer than the original route description. All of this is in scope.

Always-visible controls, each applying immediately: **Age / Grade** (multi-select over the four bands `1–3`, `3–5, Grade 1`, `5–8, Grades 1–3`, `8–12, Grades 4–7`; the summary joins selected labels with `+`, and the effective range is min-of-mins to max-of-maxes), **Children** (numeric), **Travel** (walking / bus / parent drivers), **Budget per child** (quick options plus a typed max), and **Leaving from** (the active room's address, joined to a radius select: 3, 5, 10, 30 km, or any; default 5 km).

**Mood chips** — `Fun`, `Explore`, `Active`, `Creative`, `Learn`, `Surprise me`. Match by `mood_tags` when the record carries them, else derive: fun = animals or science or a hands-on/interactive format; explore = nature or animals; active = outdoor and not comes-to-you; creative = arts; learn = museums, science or civic. `Surprise me` is exclusive of the other moods and returns three seeded-random results, ignoring the other mood filters.

**Category chips** — Animals & Farms, Nature, Museums, Arts, Science, plus Community and Comes to you in the data.

**Filter drawer** — Environment (Indoor, Outdoor, Comes to you, Free or low cost), Accessibility (Wheelchair accessible, Sensory friendly, Neurodiversity friendly, Low noise), Program type (Guided programs, Hands-on, Interactive, Self-guided). The drawer edits a **draft**: Cancel discards, Apply commits, Clear all resets. Accessibility filters are AND (every checked one must match); program type is OR. The toggle button shows the active count when closed.

**Sort** — Best match, Distance: nearest, Duration: shortest, Price: lowest. See 5.1 for how `rankFeasibleFirst` interacts.

**Exclusions, not badges** — a program is dropped from results when it is outside the radius, or when travel is walking and it is more than 2.5 km away.

**Map toggle** — shows the Leaflet panel above the results with one pin per distinct venue coordinate, plus the caption "One pin per venue in this list. The dark pin is {home}. Programs that come to you have no pin."

Search state lives in the URL (section 5.7) and matches `search_state` in the data model.

### 5.2 Trip creation

A trip is created by sending the first request. The plan screen collects rooms, date options, asks and the message; on submit, one transaction:

1. Insert the trip with `status = requested`, `status_source = system`, snapshots of room counts and costs, `relay_token`, and the resolved `venue_email`.
2. Generate tasks from section 4b of the data model. `send_request` is created already done.
3. Insert the request `message` with `is_request = true`, `party = educator`, `channel = email`.
4. Enqueue `email.send_request(trip_id, message_id)`.

Plan screen details the design fixes:

- **Rooms** are multi-select. Picking more than one sets the age range to the union, the size to the sum, and takes budget and transport from the first room. Zero rooms selected disables Send with "Pick a group and a date".
- **Date options** default to three, are ranked `1st choice`…`5th choice`, and carry a slot. Use the program's `time_slots` as the slot options when the venue publishes them; otherwise Morning / Afternoon / Either. Read mode shows ordinal + short date; edit mode exposes the date input, the slot select and Remove. Empty shows "Pick at least one date." and a lead-time warning derived from `lead_time_days`.
- **Asks are pre-selected from the catalog's gaps**: take the program's practical facts whose value matches `/not stated|not published|confirm when you book|ask when you/i`, map each through the label → question table (design map §7, "Ask questions"), keep the first four, and mark them `source = gap`. Then append the five generic topics — Lunch space, Washrooms, Bus parking, Accessibility, Indoor space available? — skipping any already covered. Plus one free-text "Add your own", `source = custom`.
- **The message preview is an editable auto-growing textarea**, pre-filled from the request template, and what the user leaves in it is what gets sent.
- Default task titles, matching the design: `Send request to {venue}`, `Book the bus`, `Director approval signed off`, `Parent consent forms out`, `Consent forms back in`, `Confirm headcount with the venue`, `Pack list, weather check, emergency contacts`. Offsets are in data model 4b; `Book the bus` is only generated when a selected room's transport is bus and the program is not comes-to-you.

The request template lives in `lib/email/templates/request.ts` and renders: greeting, centre and role, rooms with ages and counts, date options in rank order with slot, the asks as a short list, the educator's name, phone if present, and a single footer line "Sent through Fieldy, a free planner for Vancouver Island educators. Reply to this email to reach <name> directly."

### 5.3 Outbound relay (`email/send.ts`)

For every educator message:

```
From:      "<account.name> (<centre.name>) via Fieldy" <trip-<token>@mail.<domain>>
Reply-To:  trip-<token>@mail.<domain>
To:        program.booking_email or venue.booking_email
Message-ID: <trip-<token>.<message.id>@mail.<domain>>
In-Reply-To / References: previous message ids in the thread, if any
Subject:   first message: "Group visit request: <centre>, <children> children ages <a> to <b>, <first date>"
           later messages: "Re: " + the first subject
```

Store the id returned by Resend on `external_message_id`. Set the custom header `X-Fieldy-Trip: <token>` as a second way to resolve the trip if a mail system rewrites the recipient. The educator's real email appears once, in the body, below the signature. It is never in the headers.

### 5.4 Inbound relay (`email/inbound.ts`, route `/api/email/inbound`)

Verify the Resend webhook signature (Svix headers, per Resend docs) and reject anything unsigned. Resend's inbound payload references the email by id; fetch the full message (headers, text, html, attachments) with the Resend API inside the handler. Then:

1. Parse the recipient. Extract `<token>` from `trip-<token>@`. If no trip matches, or the trip is `cancelled` or `done`, return 200 and log. Do not bounce.
2. Loop guard: drop if `From` is any address on `mail.<domain>`, or if the `X-Fieldy-Hops` header is present and >= 2.
3. Write the raw message (headers plus text and html bodies as JSON) to the `mail` bucket under `raw/<trip_id>/<ulid>.json`, store the key in `message.raw_ref`.
4. Create the `message`: `party = venue`, `author_name` from the From display name or the venue name, `body` = the result of `strip.ts` on the text body (fallback to HTML converted to text). Keep the full text in `body_full`, always.
5. Attachments: download each from Resend and upload to the `mail` bucket under `att/<trip_id>/<ulid>/<name>`, record `{name, url, mime, size}` where `url` is the object key.
6. Set `trip.status = replied` and `status_source = system` if the current status is `requested`. Set `trip.last_venue_reply_at`.
7. Run the rule based classifier synchronously (it is milliseconds) and store the suggestion.
8. Schedule the notification with `after()` and return 200.

**The relay is send-only.** Fieldy emails the venue and receives what the venue sends back. Nothing is forwarded to the educator, and the educator never replies by email — they read and write in the app, which is therefore the only copy of the thread. This is a deliberate cut (spec section 3): it removes the educator inbound leg, the sender-attribution guessing that leg needs, the threading and attachment re-upload into their inbox, and one of the two ways a thread can silently diverge from what the app shows.

### 5.4a Reply notification (`email/notify.ts`)

When a venue message is stored and the account has `email_notifications`:

- To the educator's real address, `From: "Fieldy" <noreply@mail.<domain>>`, no `Reply-To`, `X-Fieldy-Hops: 1`.
- Subject: `<venue name> replied about <program name>`.
- Body: who replied, the trip and its first date, the first 200 characters of the stripped message, a button to `/trips/<id>#msg-<message_id>`, and one line: "You can't reply to this email — open the trip to answer." No attachments, no quoted thread, no suggestion text (the banner is the reason to open the app, and a wrong reading is much worse pushed into an inbox).
- Failure is recorded as `notify_error` and retried by `/api/jobs/retry`. It is never surfaced on the trip page: the message is already in the app, so a missed nudge is a missed nudge, not lost data.
- One notification per venue message. No digest, no batching in the MVP.

**Replies to the notification must not vanish.** `noreply@mail.<domain>` accepts mail at the same webhook. When the recipient's local part is `noreply`, do not resolve a trip and do not store a message: send a single auto-response per sender address per 24 hours — "Fieldy doesn't read replies to this address. Open your trip to answer the venue: <link>" — and drop it. Someone typing a real answer into that reply and getting silence is the one failure mode worth spending fifteen lines to prevent.

Loop guard still applies to both paths: drop anything whose `From` is on `mail.<domain>`, or whose `X-Fieldy-Hops` is present and >= 2.

### 5.5 Suggestion classifier (`classify/suggestion.ts`, job `message.classify`)

Only for `party = venue` messages. Rule based, deterministic, no network. Input is `body` (stripped), the trip's `date_options`, and the message timestamp as the reference date. Output matches the `suggestion` object in the data model.

Steps:

1. Split the body into sentences. Ignore anything after a signature marker or a quoted line.
2. Extract date and time mentions with `chrono-node` (`en` casual parser, `forwardDate: true`, reference date = message `sent_at`). Keep only dates within 1 to 365 days after the reference.
3. Score each sentence against three phrase lists kept in `rules.ts` as data, not code:
   - confirm: "confirm", "confirmed", "booked", "you're all set", "we can accommodate", "works for us", "see you on", "reserved", "we have you down", "looking forward to hosting"
   - decline: "unable", "unfortunately", "cannot accommodate", "fully booked", "no availability", "not able to", "closed", "we don't offer", "no longer"
   - alternative: "instead", "alternatively", "how about", "would ... work", "we could offer", "available on", "other dates", "the following dates"
   Negation within four words flips confirm to decline ("cannot confirm"). Question marks weaken confirm.
4. Decide intent:
   - a confirm sentence that contains, or is adjacent to, a date matching one of the trip's `date_options` → `confirmed`, `dates` = that date, `time` if found in the same sentence.
   - a confirm sentence with no date → `confirmed`, `dates` = null (banner offers the first date option).
   - an alternative sentence, or any extracted dates that are not in `date_options` → `proposed_dates` with those dates.
   - a decline sentence and no alternative dates → `declined`.
   - anything else, or conflicting signals of equal strength → `unclear`.
5. `confidence` = a simple score: 0.9 when one intent wins with a matching date, 0.75 when it wins without a date, 0.5 when signals conflict. Below 0.6 force `unclear`.
6. `evidence` = the highest scoring sentence, trimmed to 30 words.

Store on `message.suggestion`. Never change trip status here; only the user's tap does. The provider interface is `classify(input): Suggestion | null`; `null` means no banner.

The rule lists and the eval fixtures (M5) are the tuning surface. Expect to add phrases after the first month of real replies.

### 5.6 Applying a suggestion

Server action `applySuggestion(messageId, choice)`. The banner shows the intent sentence, the evidence in curly quotes, the action buttons and a dismiss. Copy is verbatim from the design:

- `confirmed` — "Looks like the venue confirmed {date}{ at {time}}." Button **Mark confirmed**. Sets `trip.status = confirmed`, `status_source = manual`, `confirmed_date` and `confirmed_time` from the suggestion or the chosen date option, collapses `date_options` to that one, regenerates tasks whose `offset_days` is not null relative to the new date and keeps human-edited ones. Dismiss label: **Not quite**.
- `proposed_dates` — "The venue suggested {date} or {date} instead." One **Move to {date}** button per offered date. Replaces `date_options` with that date, regenerates tasks, and pre-fills the compose box with a reply the user can send or edit: "Hi,\n\n{date} works for us — please go ahead and hold it. Same group: {n} children with {n} adults.\n\nThank you,\n{name}". Dismiss label: **Neither**.
- `declined` — "It sounds like the venue cannot take this booking." Button **Mark cancelled**, sets `status = cancelled`, `status_source = manual`. Secondary link **Find a similar program**, which opens the catalog filtered to the program's category. Dismiss label: **Not quite**.
- `unclear` — **the design does not draw this state, and that is correct.** Show the message normally with no banner and no action buttons (the classifier's safe failure per 5.5). A venue reply that only asks questions lands here; the compose box sits directly below it. There is no "needs info" intent — summarising a venue's questions in our own words is generation, not extraction, and the classifier is rule based.
- `proposed_dates` renders **one button per offered date, uncapped**. A venue offering five dates gets five buttons.
- Dismiss: set `suggestion.dismissed_at`. A dismissed banner never returns, and only the newest undismissed venue suggestion is shown.

Every status change also inserts a `system` message in the thread ("Status set to confirmed") so the thread is the audit log.

### 5.7 Auth and anonymous use

The catalog and program pages are public. Search state lives in the URL query string so links are shareable. Planning a trip, saving an outing, and rooms require a session. On first login with no centre, show the centre and first room setup as a two step form before returning to where they were.

## 8. Non functional requirements

- Every page renders useful content without JavaScript for the catalog and program pages (RSC), since links get opened inside messaging apps' browsers.
- All money is stored as numeric(10,2) and displayed with `Intl.NumberFormat('en-CA', {currency: 'CAD'})`.
- All timestamps in UTC in the database, rendered in `America/Vancouver`.
- No PII in URLs. Trip ids are ULIDs and pages require session; relay tokens are only in email headers.
- Logs never include message bodies. Log trip id, message id and job outcome only.
- The inbound webhook returns within 5 seconds; the only slow step (the notification send) runs in `after()`.
- Signed storage URLs expire in 1 hour and are generated per render, never stored.

## 10. Decisions and remaining questions

Record all of these in `docs/decisions.md`.

Settled:

- **The relay is send-only.** Fieldy emails the venue and receives their replies; the educator reads and writes in the app and gets a short notification email with a deep link, never a forwarded copy, and never replies by email. Removes the educator inbound leg, sender attribution, and thread divergence. Reversible later — the relay token infrastructure is identical either way. The educator's real address stays in the outgoing request body so the venue can always reach them directly. `account.email_forwarding` is renamed `email_notifications`; `message.forward_error` is renamed `notify_error`. Spec §3 and §5.10, plan §5.4a, four stale design strings recorded in `docs/design-map.md` §7.1.
- **No "needs info" suggestion intent.** Four intents, as the data model has them. A questions-only reply reads as `unclear` and sits in the thread with the compose box under it; summarising a venue's questions is generation, not extraction.
- **Proposed dates are uncapped.** One button per offered date.
- **Manual status selector** exists on the trip header with a "set by you" / "moved here when the venue replied" source line, and writes a system message. Not drawn in the design — invented in its language.
- **Theme.** The bright palette ships. The warm variant (`Field Trip Planner.dc.html`, `venue-map.html`) is superseded and out of scope — one theme, no alternate.
- **`booking_email`.** `outing-schema.md` v2 has it at **both** levels, program overriding venue. Resolve at import, store the result on the trip at creation as `venue_email` so later catalog edits never redirect an open thread. Added to the data model.
- **Radius.** Options 3, 5, 10, 30 km and any; default 5 km, not 2. Walking is separately cut off at 2.5 km with the reason "too far with this group".
- **Grade-based programs and daycares.** Shown, never hidden. A daycare account sees them with the school-rate flag: "School rate. Daycares are quoted through group visits — phone before you budget." Feasibility adds the reason "ages are set by grade here, not years — phone to confirm they take under-fives" when the room's oldest is 5 or under.
- **Feasibility levels.** Two — green and amber. No red.
- **Saved outings.** A tab on `/trips`, not a route. `/saved` redirects.
- **Room editor.** A modal over the Group profiles screen, not a page.
